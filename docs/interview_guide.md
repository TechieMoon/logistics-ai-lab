# 프로젝트 면접 준비

답변은 암기용 완성 대본이 아니라 실제 코드와 실험을 근거로 만드는 구조입니다. 이 프로젝트는 합성 데이터로 만든 학습용 프로토타입입니다. 회사 내부 시스템·실물류 운영·현장 비용 개선을 검증했다는 주장을 하지 않습니다.

## 90초 소개 구조

> 물류 운영에서 규정을 찾는 문제와 배송 경로를 고르는 문제를 나눠 다뤘습니다. 첫째는 합성 운영 정책에 근거한 질의응답이고, 둘째는 용량제약이 있는 경로 문제를 푸는 GNN/RL 정책입니다. [평가 사례 수]개에서 [비교 기준선]과 [실제 지표]를 비교했습니다. [실패 사례]를 분석해 [실제로 수행한 수정]을 확인했습니다. 설계·초기 구현에는 AI 지원을 사용했고, 제가 직접 이해하고 검증한 부분은 [범위]입니다. 현재 한계는 합성 데이터와 단순 거리 모델이며, 실제 적용 전에는 운영 제약과 현장 데이터를 추가해 평가해야 합니다.

대괄호는 결과 파일과 본인 학습 기록으로 채웁니다. 이해하지 못한 기술을 열거하기보다 한 가지 실패를 구체적으로 설명하는 편이 낫습니다.

## 문제 정의와 기준선

**왜 이 두 주제를 골랐나요?** 물류 업무의 지식 접근과 의사결정이라는 별도 문제를 다룹니다. 문서 답변은 근거를 확인할 수 있어야 하고 경로는 실행 가능성이 보장돼야 합니다. 두 파이프라인을 느슨하게 분리하면 각 오류와 성능을 독립적으로 평가할 수 있습니다. 실제로 둘을 연결하는 기능이 없다면 통합 운영 시스템이라고 부르지 않습니다.

**왜 CVRP인가요?** 단순 TSP는 모든 지점을 한 번 도는 거리만 보지만 CVRP는 차량 용량과 고객별 수요 때문에 창고 복귀가 필요합니다. 여기에 배송 시간창, 기사 휴식, 도로 통행시간, 다중 창고를 추가하면 다른 문제로 확장됩니다. 현재 구현한 제약과 계획만 있는 제약을 구분해야 합니다.

**왜 최근접과 2-opt를 비교하나요?** 최근접은 이해하기 쉽고 빠른 기준선입니다. 2-opt는 같은 방문 순서의 간선을 교환해 거리를 줄이는 국소 개선으로 더 강한 비교가 됩니다. 경로 내 순서만 바꾸면 경로의 총수요는 유지되지만 차량 간 이동까지 바꾸면 용량을 다시 확인해야 합니다. 2-opt도 일반적으로 전역 최적해를 보장하지 않습니다.

**학습 모델이 2-opt보다 나쁘면 실패인가요?** 현 설정에서는 더 나쁜 결과라고 명확히 말해야 합니다. 그렇다고 실험 가치가 없어지는 것은 아닙니다. 작은 문제, 적은 학습, greedy decoding, 분포 차이 등을 가설로 제시한 뒤 실제 실험으로 확인합니다. 개선이 확인되기 전에는 'RL이 더 우수하다'고 말하지 않습니다. 운영에서는 좋은 기준선을 사용하는 판단도 필요합니다.

**현재 실제 결과는 무엇인가요?** [저장된 라우팅 결과](../artifacts/routing/metrics.json)는 RTX 3060의 CUDA에서 400 step, batch 128로 학습하고 검증 데이터로 360 step checkpoint를 선택한 실행입니다. 테스트는 학습·검증과 다른 128개 합성 인스턴스, 고객 15명, 용량 30입니다. 다음 표는 그 한 번의 학습 실행에 대한 결과이며 여러 학습 seed에서의 통계적 우월성을 입증한 것이 아닙니다.

| 방법 | 평균 거리 | 평균 경로 수 (`mean_vehicles`) |
|---|---:|---:|
| 최근접 | 5.5826 | 2.9922 |
| 최근접 + 경로 내 2-opt | 5.3410 | 2.9922 |
| 학습 전 정책 | 5.4533 | 3.1953 |
| GNN + REINFORCE | 5.0010 | 3.6406 |
| GNN + REINFORCE + 경로 내 2-opt | 4.8670 | 3.6406 |

학습정책은 학습 전 정책보다 평균 거리가 **8.29%**, 최근접보다 **10.42%** 짧았습니다. 모든 평가 경로는 독립 검사에서 제약을 통과했습니다. 그러나 최근접 대비 평균 경로 수가 **2.99에서 3.64로 늘었습니다.** 코드의 차량 수 지표는 창고에서 출발해 복귀하는 경로 개수이며, 실제 기사·차량 배치나 재사용 가능성을 모델링하지 않습니다.

**거리가 짧아졌는데 왜 운영비 개선이라고 말하면 안 되나요?** 현재 목적은 거리뿐이고 차량 수 상한과 차량 고정비가 없습니다. 더 많은 경로를 쓰면서 거리만 낮추는 해가 유리해질 수 있습니다. 실제 업무가 차량 수를 제한하거나 차량·기사 투입에 고정비를 부과한다면 결과의 우열이 달라집니다. 따라서 이 결과는 합성 거리 목적에서의 개선이며 물류비 10.42% 절감이 아닙니다.

**보상 설계를 어떻게 바꾸겠나요?** 먼저 실제 제약을 확인하고 `거리비용 + 차량당 고정비 × 경로 수` 같은 목적이나 차량 수의 hard constraint를 검토합니다. 단위와 가중치를 실제 업무 자료로 정하고 같은 목적을 기준선에도 적용해야 합니다. 학습 정책에만 페널티를 주고 비교 알고리즘에는 기존 거리만 보고하면 비교가 달라집니다. 차량 수를 줄이는 것이 최우선이라면 차량 수→거리의 우선순위 목적도 검토할 수 있습니다. 이 변경은 제안이며 현재 구현된 기능이 아닙니다.

**GPU를 쓰면 더 좋은 경로가 나오나요?** GPU는 연산 장치입니다. 학습 시간을 줄일 수 있으나 목적함수나 정책 품질 자체를 보장하지 않습니다. 작은 단일 경로는 CPU가 더 빠를 수 있습니다. 모델 크기, 배치, 전송·초기화 비용을 포함한 측정 조건이 필요합니다.

## GNN과 RL

**GNN에서 그래프는 무엇인가요?** 창고·고객이 노드이고 이동 가능성 또는 거리 관계가 간선입니다. 좌표·수요 등의 특징을 이웃 정보와 집계해 노드 표현을 만듭니다. 실제 코드가 완전 그래프인지 k-nearest 이웃인지, 거리를 어떻게 반영하는지 보여 주세요. 단순히 데이터를 그래프라고 부르는 것만으로 GNN이 되지 않습니다. [GraphSAGE 원 논문](https://arxiv.org/abs/1706.02216)은 이웃 정보를 집계하는 표현 학습의 참고 자료입니다.

**GNN이 노드 수 변화에 일반화하나요?** 노드마다 가중치를 공유하면 다른 크기 입력을 처리하기 쉬울 수 있지만 성능 일반화는 별도 문제입니다. 학습보다 많은 노드, 새로운 수요, 다른 공간 분포에서 실험해야 합니다. 파라미터 공유와 평가로 입증한 일반화를 혼동하지 않습니다.

**상태·행동·보상은 무엇인가요?** 상태는 좌표·수요, 현재 위치, 방문 여부, 남은 용량 같은 정보입니다. 행동은 다음 고객 또는 창고 선택입니다. 비용은 이동거리 합이며 보상을 쓰면 그 음수로 정의할 수 있습니다. 실제 코드의 상태 표현과 보상 시점을 찾아 설명하세요.

**마스킹은 왜 필요한가요?** 방문 완료 고객, 적재 한도를 넘는 고객 등 불가능한 행동에 확률을 주지 않기 위해서입니다. 페널티만 주면 학습 중 또는 추론 시 위반 행동이 남을 수 있습니다. 모든 행동을 막아 softmax가 NaN이 되는 상태, 창고에서 창고만 계속 고르는 상태도 확인해야 합니다. 최종 경로 검사기는 정책을 신뢰하지 않고 별도로 검증해야 합니다.

**REINFORCE의 핵심은 무엇인가요?** 선택한 경로의 비용이 비교값보다 좋으면 그 경로를 선택할 확률을 높이고 나쁘면 낮춥니다. 비용 최소화 관점의 surrogate loss는 `(cost - baseline) * log_probability` 형태입니다. baseline의 gradient를 끊는지, 여러 행동의 log probability를 어떻게 합치는지, 보상 최대화로 쓰면 부호가 어떻게 달라지는지 코드로 설명하세요. 학습 기반 경로 탐색의 참고 연구는 [Attention, Learn to Solve Routing Problems!](https://arxiv.org/abs/1803.08475)입니다.

**loss가 줄면 경로도 좋아진 건가요?** 정책경사 loss는 단순 회귀의 오차와 의미가 다릅니다. baseline, log probability, 분포가 동시에 달라져 값만으로 품질을 판단하기 어렵습니다. 별도 평가 데이터에서 실제 거리와 제약 위반율을 확인합니다.

**샘플링과 greedy는 왜 나누나요?** 학습의 샘플링은 여러 선택을 경험하게 합니다. greedy는 매 단계 가장 높은 점수를 고르는 결정적 추론에 유용하지만 전역 최적은 아닙니다. 여러 경로를 샘플링한 최선과 greedy 하나를 비교한다면 추론 연산량 차이도 함께 공개합니다.

**baseline은 무엇이고 어떤 편향이 생기나요?** 행동과 무관한 baseline은 기대 gradient를 유지하면서 분산을 줄일 수 있습니다. baseline 추정 방법과 detach 여부를 확인해야 합니다. 작은 배치의 자기 비용이 batch mean에 포함되는 구현은 정확한 불편추정 관점에서 보정 이슈가 있을 수 있으므로 실제 사용 방식과 한계를 설명합니다. 구현에 없는 critic이나 PPO를 사용했다고 말하지 않습니다.

**학습했다는 증거는요?** 초기·최종 checkpoint의 파라미터 차이, optimizer step 수, 학습 log, 실제 tensor device, 평가 결과를 보여 줍니다. CUDA 사용 가능 여부만 출력하거나 loss 숫자만 존재하는 것으로 충분하지 않습니다.

**이 구현에서 실제로 쓰는 것은 무엇인가요?** [routing.py](../src/logistics_ai/routing.py)의 `MessagePassingLayer`는 거리 정보를 반영한 dense attention으로 메시지를 모으고 residual update를 합니다. `RoutingPolicy`는 4개 노드 특징을 임베딩하고, 현재 노드 표현·그래프 평균 표현·남은 용량을 문맥으로 다음 지점을 고릅니다. [train_routing.py](../scripts/train_routing.py)는 현재 모델의 greedy 경로를 baseline으로 두고 sampled 경로의 비용 차이를 detach해 REINFORCE loss를 만듭니다. PPO, DQN, 별도 value network는 사용하지 않습니다.

**거리 prior가 있는데 신경망 성과라고 할 수 있나요?** 정책 점수에 이동거리 penalty와 창고 복귀 penalty가 들어 있으므로 초기 정책부터 휴리스틱 지식이 있습니다. 학습 전 정책, 학습 후 정책, 최근접, 최근접+2-opt, 학습정책+2-opt를 구분해서 비교해야 합니다. 특히 학습정책+2-opt의 최종 개선을 모두 신경망의 성과라고 표현하면 안 됩니다.

**2-opt는 이 저장소에서 어디까지 개선하나요?** `two_opt`는 각 차량 경로 내부의 구간을 뒤집습니다. 고객을 다른 차량으로 옮기지 않아 경로별 수요는 유지되지만 차량 배정 자체의 나쁜 선택을 고치지는 못합니다. 개선량이 작다고 2-opt 전체 알고리즘이 무효라는 뜻은 아닙니다.

## RAG와 Language AI

**RAG와 fine-tuning의 차이는 무엇인가요?** RAG는 답변 시 외부 문서를 찾아 모델 입력에 넣는 접근이고 fine-tuning은 데이터로 모델 가중치를 갱신합니다. 둘은 함께 사용할 수도 있습니다. 규정이 자주 바뀌는 데모에서는 문서 갱신·근거 추적을 설명하기 쉽지만 검색 누락·낡은 문서·생성 오류는 여전히 남습니다. 개념은 [RAG 원 논문](https://arxiv.org/abs/2005.11401)을 참고하세요.

**검색기와 생성기를 따로 평가하는 이유는요?** 정답 문서가 없으면 검색 문제이고, 문서는 맞는데 숫자나 조건이 바뀌면 생성 문제입니다. 검색 hit rate만으로 답변 정확성을 말할 수 없습니다. 문서 ID가 실제로 존재하는지 검사하는 것과 그 문서가 답변을 지지하는지 판단하는 것도 다릅니다.

**왜 합성 정책을 썼나요?** 공개 가능한 데이터로 전체 파이프라인을 재현하기 위해서입니다. 실제 회사 규정을 흉내 내는 이름이나 사내 사실을 주장하지 않습니다. 합성 평가 질문은 문서와 비슷한 표현으로 만들어져 쉽게 풀릴 수 있습니다. 실제 질문 분포와 전문가 라벨이 없는 한 현장 성능으로 해석하면 안 됩니다.

**답변 불가능한 질문은 어떻게 처리하나요?** 충분한 근거가 없을 때 응답을 보류하고 관련 근거·누락 정보를 설명합니다. 유사도 threshold는 검증 데이터에서 조정할 수 있지만 threshold 자체가 사실성을 보장하지는 않습니다. 거절 성공률뿐 아니라 답할 수 있는 질문을 잘못 거절하는 비율도 봅니다.

**인용을 붙이면 hallucination이 없어지나요?** 아닙니다. 모델은 올바른 ID를 붙이면서 다른 내용을 말할 수 있습니다. 인용 문서의 실제 문장과 답의 조건·숫자를 대조해야 합니다. 자동 평가는 부분적인 신호이므로 사람이 확인한 실패 사례를 제시합니다.

**검색 문서에 '규칙 무시'가 적혀 있으면요?** 검색 문서는 신뢰할 수 있는 실행 지시가 아니라 답변의 데이터로 취급합니다. 프롬프트의 역할 분리, 필요한 내용만 전달, 도구 권한 제한, 출력 점검을 검토합니다. 프롬프트 한 문장으로 모든 주입 공격을 해결했다고 주장하지 않습니다.

**어떤 LLM을 학습했나요?** 실제로 로컬 사전학습 모델을 불러와 추론만 했다면 '사전학습 모델을 추론에 사용했다'고 답합니다. 임베딩 모델과 생성 모델을 구분합니다. 직접 사전학습·fine-tuning하지 않았다면 'LLM을 개발/학습했다'고 표현하지 않습니다. 모델이 없는 추출식 응답 모드와 실제 생성 모드를 구분해서 시연합니다.

**검색 세 가지를 왜 비교하나요?** BM25는 단어 일치에 기반한 기준선이고, E5 임베딩의 dense retrieval은 벡터 유사도로 표현 차이를 다룹니다. Hybrid RRF는 두 점수의 크기를 그대로 더하지 않고 순위를 결합합니다. RRF가 항상 낫다는 보장은 없으므로 같은 질문에서 세 방법을 비교합니다. 설정·구현이 바뀌면 실제 검색기 코드와 결과를 우선합니다. 생성 모델은 Qwen2.5-1.5B-Instruct를 선택적으로 사용하는 설계이며, 실행한 모드와 모델 revision은 결과 파일로 확인합니다.

**이 RAG 구현에서 가장 조심할 지표는요?** [rag.py](../src/logistics_ai/rag.py)의 `evidence_score`는 검색 결과의 IDF 가중 토큰 포함률 중 최댓값입니다. `calibrate_abstention`은 dev에서 정답 가능 질문 수용률에서 정답 불가능 질문 수용률의 2배를 빼는 목적값으로 threshold를 정합니다. eval 질문으로 threshold를 다시 맞추지 않습니다. 이 값은 사실일 확률도, 모든 질문 조건을 뒷받침한다는 보장도 아닙니다. 정답 가능한 질문을 거부하거나 상관없는 예외 조건을 포함하지 못하는 한계를 사례로 보여 줄 수 있어야 합니다.

**E5를 어떻게 사용하나요?** `E5Encoder.encode`는 질문에 `query:`, 정책에 `passage:` 접두어를 붙입니다. 토큰 attention mask를 고려한 평균 pooling 후 L2 정규화하고 내적으로 검색합니다. 모델 가중치는 고정하며 추론만 합니다. 이 사용법과 모델 범위는 [공식 E5 모델 카드](https://huggingface.co/intfloat/multilingual-e5-small)를 확인합니다.

**생성 응답이 바로 최종 답인가요?** 이 구현은 원문 근거와 `model_draft`를 분리하고 초안에 `verified=false`를 표시합니다. `citation_check.valid_syntax_only`는 인용 ID 형식과 허용 목록을 점검하는 제한적 검사입니다. 답변이 인용 문서와 의미상 일치하는지는 보장하지 않습니다. [Qwen 모델 카드](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct)에 소개된 사전학습 모델을 사용하지만 이 합성 물류 질문에서의 성능은 저장소의 평가 결과로 별도 판단해야 합니다.

## 실험·재현성·운영

**데이터 누수는 어떻게 막았나요?** 학습용과 평가용 인스턴스 생성 seed를 분리하고 같은 평가 데이터를 여러 알고리즘에 제공합니다. 평가를 보며 계속 설정을 바꾸면 평가 세트도 사실상 검증용이 됩니다. 최종 성능 주장이 필요하면 별도 holdout을 남깁니다. RAG에서 검색 코퍼스에 정답 문서가 있는 것은 목적에 맞지만 평가 질문을 그대로 학습·규칙에 넣는 것은 별도 문제입니다.

**지표 숫자가 무엇을 뜻하나요?** 분모, 사례 수, 실패 처리, 정규화 방식부터 말합니다. 평균 거리, 기준선 대비 차이, 제약 위반율, 지연 시간을 함께 봅니다. 시간 측정은 모델 로드 포함 여부와 warm-up, 배치 크기를 공개합니다. CUDA 연산은 비동기이므로 정확한 GPU 실행시간 측정에서는 동기화 또는 CUDA event가 필요합니다. [PyTorch CUDA 안내](https://docs.pytorch.org/docs/stable/notes/cuda.html).

**한 번 잘 나온 seed만 쓰면 안 되나요?** 결과가 운에 좌우될 수 있습니다. 여러 seed의 평균과 분산, 또는 최소한 반복별 원값을 보여 줍니다. 작은 데모에서 통계적 우월성을 주장하지 않습니다. 같은 seed라도 장치·라이브러리 차이로 결과가 달라질 수 있습니다. [PyTorch 재현성 안내](https://docs.pytorch.org/docs/stable/notes/randomness.html).

**실제 배송에 배포하려면 무엇이 더 필요한가요?** 실제 도로 이동시간, 시간창·차량·기사 제약, 데이터 품질, 운영 담당자의 경로 검토, 모니터링, 장애 시 기준선 복귀가 필요합니다. 우선 실제 제약을 명세하고 작은 과거 데이터로 기존 방식과 비교한 뒤, 결과를 사람이 검토하는 단계부터 시작하겠다고 설명합니다. 이 저장소가 그 기능을 이미 제공한다고 말하지 않습니다.

**개인정보나 회사 문서를 넣어도 되나요?** 현재는 합성 데이터만 공개합니다. 실제 데이터 적용은 접근권한·보존·공개 범위·모델 제공자 전송 여부를 정한 뒤 진행해야 합니다. 공개 저장소에는 인증 정보, 이력서, 고객 주소, 사내 정책을 넣지 않습니다.

## AI 협업을 묻는 질문

**이 코드를 직접 만들었나요?** 최초 설계·구현·문서화에 AI 지원을 사용한 범위부터 정확히 밝힙니다. 이어서 본인이 읽고 재현한 부분, 고친 버그, 직접 설계한 실험을 구체적인 diff·로그로 보여 주세요. 아직 학습 전이라면 완료된 본인 작업처럼 말하지 않습니다.

**AI가 틀린 제안을 했을 때 어떻게 했나요?** 실제 사례로 `요구조건 → AI 제안의 문제 → 재현 입력 → 수정 → 통과한 검사 → 남은 한계`를 답합니다. 없었던 디버깅 경험을 만들지 말고 이 문서의 실습으로 직접 사례를 만드세요.

**지금 기능 하나를 바꿔 보세요.** 먼저 수용 조건을 말하고 관련 코드·검사를 찾습니다. 가장 작은 변경을 적용한 뒤 정상·경계·실패 사례를 확인하고 diff를 설명합니다. AI가 만든 코드를 붙여 넣은 후 통과 여부만 말하지 않습니다. 테스트 도구 사용 규칙은 실제 전형 안내를 따릅니다.

## 5분 데모 순서

1. README의 실행 절차로 로컬 API를 켜고 `/docs`를 엽니다. [api.py](../src/logistics_ai/api.py)의 Swagger UI를 사용하는 데모이며 별도 제품용 화면은 없습니다.
2. `/health`에서 CUDA 가능 여부와 checkpoint 존재 여부를 확인합니다. 이것만으로 학습 완료를 주장하지 않고 결과 보고서를 함께 보여 줍니다.
3. `/route`에 동일 seed·고객 수·용량으로 `nearest_neighbor`, `two_opt`, `learned`, `learned_two_opt`를 요청합니다. 거리, 유효성, 사용 차량 수를 비교하고 거리 단위가 km가 아님을 설명합니다.
4. `/ask`에서 먼저 검색 근거를 보고, 실제 모델을 준비한 뒤 `generate=true`의 생성 결과를 비교합니다. 기본값은 `generate=false`이므로 기본 실행을 LLM 생성이라고 소개하지 않습니다.
5. 근거 없는 질문이나 경계 사례 하나를 보여 준 뒤 실험 보고서의 한계를 말합니다. 데모 성공 화면만 고르지 않습니다.

## 코드 읽기·수정 실습

아래 과제는 면접 연습입니다. 이미 구현된 동작이면 재구현하지 말고 검사와 설명으로 검증하세요. 기능이 없는 경우 계획과 현재 상태를 구분합니다.

| 과제 | 관찰 포인트 | 통과 기준 |
|---|---|---|
| 고객 3명 사례 손계산 | 창고 복귀 포함 거리와 수요 | 코드 결과와 손계산 일치 |
| 용량 경계 사례 | 수요=남은 용량, 수요>용량 | 전자는 허용, 불가능한 입력은 명확히 거부 |
| 한 고객 중복·누락 경로 | 정책 외부 유효성 검사 | 짧은 경로라도 실패로 판정 |
| 작은 forward shape 추적 | batch, node, feature 축 | 각 연산의 입력·출력을 설명 |
| 학습률 한 변수 변경 | 동일 초기화/평가 데이터 | 전후 지표·해석·실패 포함 기록 |
| 동의어 질문 추가 | 키워드 의존성과 의미 검색 | 검색 근거와 생성 답변 따로 판정 |
| 없는 예외 규정 질문 | 추측·응답 보류 | 없는 정책을 사실처럼 말하는지 기록 |
| 문서 수치 변경 | 색인 갱신과 캐시 | 새 버전 근거를 읽는지 확인 |
| 모델 파일 없는 환경 | fallback 및 오류 메시지 | 실제 생성 여부가 사용자에게 드러남 |
| 결과 재현 | 명령·seed·버전·데이터 | 다른 시점에 같은 조건으로 실행 가능 |

학습 노트에는 `내 예측`, `실제 결과`, `차이의 이유`, `다음 실험` 네 항목을 남깁니다. 모든 질문에 바로 답할 필요는 없지만, 무엇을 알고 무엇을 더 확인해야 하는지 구분할 수 있어야 합니다.
